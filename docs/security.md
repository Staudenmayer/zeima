# Security

The first white-box assessment of the code (commit `70c8d36`, 18 November 2026; the report is
[`Zeima-Security-Assessment.pdf`](Zeima-Security-Assessment.pdf)) found no critical issue, 2 high, 10 medium,
8 low and 2 informational ones. This page says what was done about each, where the fix lives and how it is tested.
A re-assessment of the fixes ([`Zeima-Security-Re-Assessment.pdf`](Zeima-Security-Re-Assessment.pdf)) found no high or medium finding left and
listed nine low and informational remainders (R-1 to R-9, below); they are handled too.
**Not yet done:** a penetration test of a running installation, which both reports leave open, and the items marked *open*.

## Findings

| ID | Finding | Status | Where, and what to know |
|---|---|---|---|
| ZE-01 | SSO metadata fetched by Keycloak (DNS rebinding, unvalidated endpoints) | Fixed | The **API** reads the provider's metadata itself (`fetchMetadata` in `server/src/modules/orgs/sso.ts`): the connection goes to the address that was checked, no redirects, 1 MB and 10 s limits. Keycloak only *parses* the document it is handed (multipart `import-config`) and fetches nothing. Every address in the result (`tokenUrl`, `jwksUrl`, …) must be public too. Keycloak still contacts the provider at each sign-in: block its egress to private ranges (network policy, `docs/admin-guide.md`). |
| ZE-02 | Domain ownership not verified by default; SCIM pulls in and disables other tenants' users | Fixed | `SSO_VERIFY_DOMAINS` is **on by default** in both modes (an installation of one company may switch it off). SCIM never adds an existing account (the person is invited and joins when they accept), marks an address verified only when its domain was proven, and never disables an account that belongs to another organization (it only removes the person from this one). |
| ZE-03 | Sync accepts any timestamp | Fixed | A change stamped more than 2 minutes ahead of the server is refused (`clock_ahead`, `server/src/sync/merge.ts`, mirrored in the app's `Reason`). A non-manager's no-op write of `locked` loses its stamp so it cannot outrank a manager's decision. |
| ZE-04 | Addon trust, hash and consent all come from the server; the backend never checks consent | Fixed | The vendor's keys are compiled in (`ZEIMA_ADDON_VENDOR_KEYS` at build, `src-tauri/src/registry.rs`); keys a server hands out are shown as **"server trusted"**, never as the vendor's, and cannot take over a vendor key id. The **app itself asks** (native dialog, `install_package`) before every install and update and lists what is new; an update never gets a permission without that. *Open: the vendor's own signing key has to be made and set at build time.* |
| ZE-05 | Registry package written to a predictable temp path after the hash check | Fixed | The verified bytes are parsed in memory (`read_package_bytes`); nothing is written and read back. |
| ZE-06 | Public proxy exposes Keycloak's admin console, master realm and internal API routes | Fixed | Caddy and the Helm ingress pass only `/realms/zeima`, `/resources` and `/robots.txt` on the sign-in host (`exposeKeycloakAdmin` to override). Keycloak's events and `/metrics` are served on a **second port** (`INTERNAL_PORT`, 3001) and are 404 on the public one, whatever the proxy forwards. |
| ZE-07 | Open self-registration, email verification off by default | Fixed (partly) | `VERIFY_EMAIL` is **on by default**; Helm refuses to install with it on and no `smtp.host`. Registration stays available by default (new invitees register through it) but `REGISTRATION_ALLOWED=false` closes it for installations whose people come in through SSO, a directory, SCIM or an administrator. |
| ZE-08 | API connects to PostgreSQL as owner/superuser; RLS reversible from the session | Fixed (partly) | With `APP_DATABASE_PASSWORD` (required by the compose file, generated by Helm) requests run through a **separate pool that logs in as `zeima_app`**: no superuser, no `BYPASSRLS`, and no way back to the owner (`withUser`, `server/src/db/index.ts`; tested in `server/test/db.test.ts`). The owner connection remains for migrations and the few server-side jobs (identity mirror, SCIM, billing). `FORCE ROW LEVEL SECURITY` is not applied: the owner of the standard images is a superuser, who bypasses it anyway. |
| ZE-09 | Over-privileged Keycloak service account | Fixed (partly) | `manage-realm`/`view-realm` are **no longer given by default**; only the company directory needs them, and the API says so when Keycloak refuses (`directory_needs_role`). `manage-users` stays: SCIM, invitations and disabling accounts need it. Rotate `API_ADMIN_SECRET` on a schedule and keep it in a secret manager. |
| ZE-10 | Client trusts server-supplied issuer, API URL and links | Fixed | `src-tauri/src/trust.rs`: the sign-in and API addresses must be https (plain http only for a development server on this machine) and on the **same site** as the server the person typed; the OIDC endpoints must be https on the issuer's site. Only `https:`, `mailto:` (and http on this machine) links are opened, for every link. A server whose sign-in lives on another site is refused. |
| ZE-11 | Vulnerable dependencies; no audit step | Fixed | 26 JavaScript and 39 Rust advisories worked through (`bun audit fix`, overrides, `cargo update`, `zip` 9, `sqlx` 0.9.1). CI runs `bun audit --audit-level=high` and `cargo audit` on every change and weekly; Dependabot keeps them current. One accepted advisory with a reason in `.cargo/audit.toml` (bundled SQLite in sqlx, needs a crafted `-wal` file next to the person's own database). *Open: one moderate advisory remains in `esbuild`, used by build tools only (the development server it affects is not run on a person's machine).* |
| ZE-12 | Checkout metadata is unsigned | Fixed | The purchase link carries a token only this server can make for that user and organization (`checkoutToken`); the webhook refuses events without a valid one. |
| ZE-13 | Fail-open defaults | Fixed | `NODE_ENV` defaults to production; API docs and metrics default to off; a route that declares neither `security` nor `config.public` **stops the server from starting** (`buildApp`, tested). |
| ZE-14 | Tauri hardening gaps | Fixed | Developer tools are off in release builds; the organization proxy refuses percent-encoded paths; each window is limited to the commands it needs (R-2 below). `style-src` keeps `unsafe-inline` (accepted, see R-2). | |
| ZE-15 | Rate limit by address only; trust-proxy accepts any address | Fixed | `TRUST_PROXY` takes a hop count or ranges (compose and Helm use `1`); per-account budgets on sync pushes; 10 sockets per account; a separate limit for SCIM. |
| ZE-16 | Webhook HMAC has no timestamp; challenge secret falls back to a constant | Fixed | The signature covers `<timestamp>.<body>`; calls more than 5 minutes old are refused (listener and API). The domain proof uses `SSO_CHALLENGE_SECRET` or the Keycloak admin secret and never a built-in value. **Rebuild Keycloak** (`--build`) so the listener sends the timestamp. |
| ZE-17 | Local database and backups unencrypted, no explicit permissions | Fixed (partly) | Data folder and backups are owner-only (`0700`/`0600`, `crates/zeima-core/src/fsperm.rs`). Encryption at rest is **not** added: use full-disk encryption on managed machines (documented); SQLCipher is a possible later step. |
| ZE-18 | Containers and Kubernetes objects lack hardening; images and actions not pinned | Fixed (partly) | `no-new-privileges`, dropped capabilities, read-only file systems where the image allows, memory limits (compose); security contexts on every pod, default-deny `NetworkPolicy` (Helm); base images pinned by digest; GitHub Actions pinned to commits. *Open: a protected GitHub environment with required reviewers for the signing secrets is a repository setting.* |
| ZE-19 | Last-owner check not atomic; server can replace bundled legal profiles | Fixed | Owner changes take a per-organization lock and re-check under it (tested with two owners demoting each other at once). A profile the **server** serves can add countries but not replace a bundled one; replacing takes a file in the folder on the machine. |
| ZE-20 | Profile pictures validated by text pattern only | Fixed | The header is read: the bytes must be the declared type, at most 512×512 pixels (`server/src/modules/me/image.ts`). |
| ZE-21 | Roles apply at token refresh | Accepted | Up to five minutes (token lifetime); disabled accounts are refused within 15 seconds. |
| ZE-22 | Self-hosted plan enforcement is client-side | Accepted | A business decision: a self-hosted installation's license is checked by the app. |

## Remainders of the re-assessment

| ID | Remainder | Status |
|---|---|---|
| R-1 | Self-registration open by default | Fixed: it is a **decision**. The compose file does not start until `REGISTRATION_ALLOWED` is `true` or `false`; the Helm chart does not install until `keycloak.registrationAllowed` is set. |
| R-2 | The web view can call every command; inline styles allowed | Fixed (commands), accepted (styles). The app declares its commands to Tauri (`src-tauri/build.rs`) and the **quick switch and prompt windows get only the 41 of 149 commands their code can reach** (no addon install, organization API, export, purchases or links); the main window keeps all. The capability files are generated by `scripts/tauri-capabilities.mjs` and a test keeps them current. Styles: `style-src` keeps `'unsafe-inline'` because UI libraries (found by running the built app under a strict policy) inject `<style>` elements; scripts stay `'self'` only, so an injected page cannot run code. A leftover import of Google Fonts was removed. |
| R-3 | Provider addresses are checked once; Keycloak's outbound traffic is open | Fixed (second layer): see R-4. A name that changes its DNS answer later can no longer reach private addresses from Keycloak or the API when the egress policy is on. |
| R-4 | Network policies cover inbound traffic only | Fixed (Helm): egress policies for the API and Keycloak allow DNS, each other, the database and **public** addresses only (https, and the mail port for Keycloak); private ranges, link-local and the cloud metadata address are blocked. Internal mail, directory or database servers go in `networkPolicy.egressAllowCidrs`. Compose: the database is on an internal network with no way out; restrict Keycloak's outgoing traffic with your host firewall (docs/admin-guide.md). |
| R-5 | Vendor key protection depends on the release variable | Fixed: the release workflow **fails** for a final release when `ZEIMA_ADDON_VENDOR_KEYS` is empty (and warns for a pre-release). |
| R-6 | SCIM reveals that an account exists | Fixed: the 409 for an existing account is word for word the one for a person who is already a member. |
| R-7 | Without `APP_DATABASE_PASSWORD` the weaker role arrangement is used silently | Fixed: the API logs a warning at start-up. (`FORCE ROW LEVEL SECURITY` stays off: the owner of the standard images is a superuser, who bypasses it.) |
| R-8 | Rust crates were not scanned locally | Fixed: `cargo audit` was run (39 vulnerabilities, all but one upgraded, one accepted with a reason in `.cargo/audit.toml`) and runs in CI. Extism and wasmtime (the addon sandbox) are on current patch releases; Dependabot keeps them there. |
| R-9 | Local database unencrypted | Accepted and documented: `docs/admin-guide.md`, "Managed machines". |

## Run for real

Besides the tests, the hardened chart was installed on a Kubernetes cluster (kind on Podman): PostgreSQL and Keycloak as non-root, the API through
the restricted database login, the sign-in and sync end-to-end check (`deploy/e2e/smoke.mjs`) passing, `/metrics` and `/v1/internal/*` answering 404 on the public
port, and the network policies enforced (a pod could reach a public address and the services it needs, but not the metadata address, Keycloak's
management port or the API's internal port). The single sign-on flow was run against a real Keycloak (`E2E_SSO=1 deploy/e2e/org-smoke.mjs`) after the metadata
fix. Not run: the Docker Compose stack with its proxy, and the desktop app's windows with the new command scoping (the capabilities are validated when the app is
built and kept current by a test, but nobody has clicked through the quick switch and prompt windows yet: please do, once, before a release).

## Checks that keep these fixed

Regression tests exist for the cases in the report's section 7.1 and for most findings: far-future clocks and the no-op lock
write (`server/test/orgsync.test.ts`), DNS rebinding, redirects and internal addresses in provider metadata
(`server/test/sso.test.ts`), SCIM and another organization's accounts (`server/test/provisioning.test.ts`), the
proxy and ingress paths, hardening and pinned digests (`server/test/deploy.test.ts`), the internal port
(`server/test/internal-listener.test.ts`), the route guard and quotas (`server/test/route-guard.test.ts`), the restricted
database login (`server/test/db.test.ts`), the checkout token (`server/test/billing.test.ts`), pictures
(`server/test/avatar.test.ts`), and on the app side the trusted addresses and links (`src-tauri/src/trust.rs`), the
addon question and packages (`src-tauri/src/commands_addons.rs`), the registry keys and rules
(`src-tauri/src/registry.rs`), file permissions and the server's profiles.
